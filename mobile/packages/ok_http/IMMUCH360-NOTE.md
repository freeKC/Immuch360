Kotlin side that Dart does not call need nothing.

JNI receivers (crash family F2 of release 44, `Immuch360` mark at the top of `lib/src/jni/bindings.dart`). The
bindings of jnigen 0.15 passed the receiver of each instance call as `reference.pointer` read on `this`, a `JObject`,
which is not `Finalizable`: nothing kept the receiver reachable during the native call, so a garbage collection in
that window could run its finalizer and delete its JNI global reference while ART was about to use it, a SIGSEGV in
`art::InvokeVirtualOrInterfaceWithVarArgs` under `globalEnv_CallObjectMethod` (Play and Meta crash reports of
November 2026). jnigen 0.17.0 binds the reference to a local first (dart-lang/native#3346); `tool/hoist_receivers.py`
applies that form to the 540 instance members of the file: `final _$$selfRef = reference;` as the first statement,
`_$$selfRef.pointer` as the receiver. The static members (`_class.reference.pointer`) are unchanged. After the
bindings are generated again with a jnigen older than 0.17, run `python3 tool/hoist_receivers.py` (it rewrites the file
and checks that no receiver use is left); `mobile/test/infrastructure/ok_http_receivers_test.dart` fails while one is.
This change can go once the bindings come from jnigen 0.17 or later.

JNI objects released after use (same family, `Immuch360` comments in `lib/src/ok_http_client.dart` and
`lib/src/ok_http_web_socket.dart`). `OkHttpClient.send` used to chain calls on temporaries and leave every object it
made (the builders, each `addHeader` result, the strings, the per request client, the response, its headers, each
chunk of the body, the exceptions) to the Dart garbage collector. Each one is now held in a local and released right
after its last synchronous use. A release is itself a use, so the object stays reachable through every call before
it, the helpers of package:jni 0.15 included, which call Java on `this` without keeping it (`JObject.toString` of an
exception, the `JMap` of `toMultimap`, `JString.toDartString` without `releaseOriginal`); and the global references
go at once, which also stops their growth reported in immich-app/immich#30972. The call, the request body and the
reader of the response are used by callbacks after `send` returns: `_RequestObjects` releases them together once the
call is over (body read to its end, failure, or refused response) and the streaming of the request body has ended;
an abort that comes later leaves the finished call alone. A chunk of the response body is copied with one
`getRange` instead of one JNI call per byte. In `ok_http_web_socket.dart`, `_connect` does the same for the opening
request, and the text of a message, of a close reason and of a failure is read before the object is released. The
callbacks and listeners handed to Java are released on the Dart side once Java holds them: their port lives as long
as the Java proxy does (`PortCleaner` of package:jni), not as long as the Dart reference.

When upstream Immich moves the ok_http ref of `mobile/pubspec.yaml`, copy `pkgs/ok_http` of the new ref here and apply
the changes below again (every change is marked `Immuch360`). The copy can go once upstream ok_http follows a relative
`Location` itself.

What differs from upstream, to apply again when a newer commit is copied here:

1. Redirects (8 November 2026), `android/src/main/kotlin/com/example/ok_http/RedirectInterceptor.kt`. The loop of
   upstream gave the raw `Location` header to `Request.Builder.url`, which only takes absolute http and https URLs: a
   relative `Location` (`/api/...`, allowed by RFC 9110 section 10.2.2, sent by some reverse proxies and sign in
   gateways) threw an IllegalArgumentException on OkHttp's dispatcher thread, which OkHttp rethrows there, and the
   app ended (Meta Horizon build 3030023; upstream Immich issues 28535 and 30132). The loop now follows OkHttp's own
   rules (RetryAndFollowUpInterceptor of OkHttp 4.12) but for one:
   - the `Location` is resolved against the request URL (`HttpUrl.resolve`); a missing one, or one that is not an
     http or https URL, is not followed and the caller gets the redirect;
   - `maxRedirects` is clamped to 0..20 (OkHttp's own limit); reaching it closes the answer and throws
     `IOException("Redirect limit exceeded")`, the text the Dart side maps, so the package:http conformance cases
     keep their results;
   - 303 after any method but GET, HEAD and PROPFIND is followed with a GET without body, `Content-Type`,
     `Content-Length` and `Transfer-Encoding`;
   - 300, 301, 302, 307 and 308 keep the method and the body. This is the one difference from OkHttp, which turns
     301 and 302 into a GET: RFC 9110 allows keeping them, upstream ok_http and upstream Immich keep them, and a GET
     would break a sign in sent to http:// behind a 301 to https://. OkHttp's rule is one condition away
     (`code != 307 && code != 308` instead of `code == 303`);
   - a one-shot body (`StreamingRequestBody`, the streamed and multipart uploads) is never sent again: the caller
     gets the redirect;
   - `Authorization` is dropped when the scheme, the host or the port changes;
   - any RuntimeException of the interceptor or below becomes an IOException with it as the cause, which the Dart
     side gets as a `ClientException` instead of the app ending;
   - `onRedirectReceived` gets the resolved URL;
   - `RedirectInterceptor.onUnusualRedirect` (new, null by default) is told, once per process for each host of the
     request, status and kind, of a relative `Location` that was resolved, a `Location` that could not be, and a
     one-shot body that stopped a redirect, in a text without query string or user info. The app sets it in
     `MainActivity.registerPlugins` to `AppHealth.report("network", text)`, which writes it to the Logs page.

   Tests: `mobile/android/app/src/test/kotlin/app/alextran/immich/core/OkHttpRedirectTest.kt` (the plugin is on the
   app's test classpath).
